# Issue B3.1 Solution — AssignmentEngine Orchestration (`execute_run`)

## 1. Architectural Pattern Applied & Rationale
- **Pattern:** **Facade / Service Orchestrator Pattern** implementing the **Internal Component Contract (`AssignmentEngineContract`)** together with a **Strategy Pattern Registry (`self.strategies`)** and **Repository Pattern Synchronization**.
- **Rationale:** Component A (Flask Visualization & Recommendation UI) communicates with Component B (Assignment Engine) exclusively via `AssignmentEngineContract.execute_run(request)`. Implementing `AssignmentEngine.__init__` and `AssignmentEngine.execute_run` in `app/engine/solvers.py` connects the domain validation rules (`app.domain.validation`), Pyomo/HiGHS MILP strategies (`app.engine.strategies`), analytical indicators (`app.engine.metrics`), and SQLite repositories (`app.persistence.repositories`) into a single headless workflow—replacing the `MockAssignmentEngine` fallback while keeping `AssignmentStrategy` in `app/engine/solvers.py`.

## 2. High-Level Logic & Data Flow Walkthrough
1. **Strategy Registration (`__init__`):** Instantiates and registers `PreferenceOrientedSolver` (`"PREFERENCE"`), `SkillFitOrientedSolver` (`"SKILL_FIT"`), and `BalancedTradeoffSolver` (`"BALANCED"`) in `self.strategies`.
2. **Pre-Solver Validation (`validate_inputs`):** Validates the `RunRequest` cohort. If mathematically infeasible (`not val_outcome.is_feasible`) or structurally invalid (`not val_outcome.is_valid`), constructs an `AssignmentRun` with status `INFEASIBLE` or `INVALID_INPUT`, records diagnostic reasons/errors, persists the run via `self.run_repo.save_run(run)`, and returns without crashing.
3. **Entity Synchronization:** Saves skills (including any uncatalogued skills referenced by students or projects), projects, students, and fixed assignments via their repositories to guarantee SQLite foreign-key integrity before saving solutions.
4. **Multi-Alternative Generation with No-Good Cuts:** Rotates through the registered strategies starting with `request.strategy_key` (`PREFERENCE` → `SKILL_FIT` → `BALANCED`) up to `request.max_alternatives`, passing previously found allocations in `excluded_solutions` so every generated `models.Solution` is strictly distinct.
5. **Indicator Calculation & Persistence:** Computes feasibility, efficiency, fairness, and capacity indicators for each solution via `metrics.compute_solution_indicators`, attaches them to `models.Solution` objects numbered from `1`, saves the `AssignmentRun` via `self.run_repo.save_run(run)`, and returns it.

## 5. Pedagogical Checkpoint — Check Your Understanding
1. **Why must `execute_run` synchronize skills, projects, and students to the database before calling `self.run_repo.save_run(run)`?**
   - SQLite enforces `PRAGMA foreign_keys = ON`. The `assignments` table references `students(id)` and `projects(id)`, and `student_skills` / `project_requirements` reference `skills(id)`. Synchronizing entities first guarantees that headless callers (such as unit tests passing in-memory `RunRequest` objects) never trigger foreign-key violations.
2. **How does `execute_run` generate 3 distinct Pareto perspectives on the Standard Scenario while still supporting multiple alternatives on cohorts where two strategies share the same unconstrained optimum?**
   - It rotates through `strategy_order` (`PREFERENCE`, `SKILL_FIT`, `BALANCED`) while passing `excluded_solutions` (integer no-good cuts $\sum_{(s,p) \in A^{(k)}} x_{s,p} \le |S| - 1$) across every solve iteration, forcing each subsequent solve to find the best remaining distinct allocation.
