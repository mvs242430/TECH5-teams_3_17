## 1. Architectural Pattern & Design Rationale
- **Pattern Applied:** Strategy Pattern (`AssignmentStrategy` ABC with concrete subclasses `PreferenceOrientedSolver`, `SkillFitOrientedSolver`, and `BalancedTradeoffSolver`).
- **Why Chosen:** The Strategy Pattern allows `AssignmentEngine` to switch or combine objective functions (`PREFERENCE`, `SKILL_FIT`, `BALANCED`) interchangeably while reusing the common `solve()` template method and `_build_base_model` constraint builder.
- **Component Scope:** `app/engine/strategies.py`, `tests/test_solvers.py`.

---

## 2. High-Level Logic & Data Flow Walkthrough
1. **`PreferenceOrientedSolver` (`name="PREFERENCE"`):**
   - Maximizes student preference satisfaction: assigns utility $M - \text{rank}_{s,p} + 1$ for ranked projects (where $M = \max_s |\text{preferences}_s|$) and imposes a heavy penalty $-2M$ for unranked projects.
2. **`SkillFitOrientedSolver` (`name="SKILL_FIT"`):**
   - Maximizes aggregate fractional skill fit $f_{s,p} \in [0.0, 1.0]$ computed via `metrics.calculate_assignment_skill_fit(student, project)`.
3. **`BalancedTradeoffSolver` (`name="BALANCED"`):**
   - Maximizes a weighted convex combination $w_{\text{pref}} \cdot \tilde{u}_{s,p} + w_{\text{skill}} \cdot f_{s,p}$ (default $0.5 / 0.5$) where normalized preference utility $\tilde{u}_{s,p} = (M - \text{rank}_{s,p} + 1)/M$ for ranked choices and $-1.0$ for unranked choices.
4. **Graceful Infeasibility Handling in `solve()`:**
   - Invokes HiGHS with `load_solutions=False` so that when `termination_condition` is not `optimal` or `feasible` (e.g., Scenario 3 Capacity Deficit), `solve()` returns `("INFEASIBLE", [], None, diagnostics)` cleanly without raising an exception.

## 5. Check Your Understanding (Pedagogical Checkpoint)
1. *Why do we normalize preference utility to $[0, 1]$ inside `BalancedTradeoffSolver` before combining it with skill fit?*
   - **Defense:** Raw preference utility scales with $M$ (e.g., $1$ to $3$), whereas `skill_fit_score` is always in $[0.0, 1.0]$. Normalizing both terms to the same $[0, 1]$ scale ensures the $50/50$ weights reflect a true equal trade-off rather than letting raw rank numbers dominate.
2. *Why do we pass `load_solutions=False` to `model.solver.solve(model, load_solutions=False)`?*
   - **Defense:** In Pyomo's APPSI HiGHS interface, attempting to auto-load variable values when a problem is mathematically infeasible raises a `RuntimeError` / `PyomoException`. Checking `result.solver.termination_condition` before calling `model.solutions.load_from(result)` guarantees graceful `"INFEASIBLE"` status reporting.
