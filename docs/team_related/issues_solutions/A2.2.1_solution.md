# Issue A2.2.1 Solution & Architectural Rationale

**Issue Title:** Issue A2.2.1 — Dedicated Solutions Hub Page & Integrated Decision Guide

**Author / Lead:** Team A (Visualization & Recommendation)  

---

## 1. Architectural Pattern & Design Rationale
- **Pattern Applied:** **Model-View-Controller (Flask Blueprint) + Master Layout Active-Route Resolution + Progressive Disclosure Presentation**
- **Why Chosen:**
  - Previously, the top navigation bar offered 6 data-input tabs (`Students`, `Projects`, `Preferences`, `Fixed Locks`, `Skills`, `Scenarios`), `Dashboard`, and `Compare`, with **no top-level destination for generated Solutions**. Users inspecting `/runs/<id>`, `/solutions/<id>`, or `/recommendations/<id>` saw `Dashboard` highlighted as active in `base.html`, yet clicking `Dashboard` lost their solution view.
  - Adding a dedicated `Solutions` hub (`GET /solutions`) immediately next to `Dashboard` balances input and output navigation for all three roles (`ADMIN`, `COORDINATOR`, `STUDENT`).
  - Rather than duplicating recommendation algorithms in the controller or cramming full multi-paragraph policy justifications onto the overview screen, `solutions_overview()` reuses `app.engine.recommendations.generate_recommendations()` read-only and applies **Progressive Disclosure**: winning policy badges appear directly on each Solution Card alongside a compact 3-column **Decision-Support Policy Guide**, linking to `/recommendations/<run_id>` for full **Calculated Evidence vs. Policy Advice** inspection.
- **Component Scope:** Strictly confined to **Component A (`app/visualization/`)**, documentation (`docs/architecture.md`), and visualization tests (`tests/test_visualization_component.py`). Zero changes to `app/engine/`, `app/contract/`, or `app/persistence/`.

## 2. High-Level Logic & Data Flow Walkthrough
1. **Navigation & Active Tab Resolution (`base.html` & `style.css`):**
   - `Solutions` (`url_for('visualization_web.solutions_overview')`) sits immediately after `Dashboard` for all roles.
   - `Dashboard` receives `class="active"` exclusively on `visualization_web.dashboard`.
   - `Solutions` receives `class="active"` across `solutions_overview`, `view_run`, `view_solution`, and `view_recommendations`, giving every solution/recommendation view a consistent parent tab.
   - `.nav-links` gap and font-size are refined (`gap: 1rem; flex-wrap: wrap; font-size: 0.92rem; white-space: nowrap;`) so all 9 Administrator tabs fit comfortably on laptop viewports.
2. **Run Selection & Stale-Cohort Detection (`routes.py` -> `solutions_overview`):**
   - Queries `RunRepository.list_runs(limit=25)` and `RunRepository.list_solution_ids_with_assignments()`.
   - If `?run_id=<id>` is provided: loads `RunRepository.get_run(requested_run_id)`, or flashes `"Run '<id>' not found."` (`danger`) and redirects to `/solutions` if unknown.
   - If `?run_id` is omitted: selects the newest run that still holds active student assignments (`any(s.id in usable_ids for s in r.solutions)`), falling back to `recent_runs[0]` when all runs are infeasible/emptied, or `None` when zero runs exist.
   - Flags `is_stale_run = True` if a historical run's student assignments were cascaded away by a cohort reset, displaying a clear notice and omitting unusable comparison links.
3. **Recommendation Mapping & Privacy Gating (`routes.py` -> `solutions.html`):**
   - Calls `recommendations.generate_recommendations(selected_run.solutions)` and builds `solution_badges: dict[str, list[tuple[int, str]]]` mapping each `recommended_solution_id` to its `(priority_index, priority_focus)` tuples so card badges match the color coding and anchor links (`#rec-1`, `#rec-2`, `#rec-3`) of `/recommendations/<run_id>`.
   - Enforces `can_view_records` on solver diagnostics (hiding student-naming warnings from `STUDENT`) and `can_optimize` on `New Run` and `Clear All Solutions` controls.

## 5. Check Your Understanding (Pedagogical Checkpoint)
Key self-check questions for student grading defense:
1. *Why does `solutions_overview()` check `list_solution_ids_with_assignments()` when choosing the default run?*
   - Loading a new scenario deletes old students, which cascades to `assignments` while leaving historical rows in `assignment_runs` and `solutions`. Preferring the newest run with active assignments ensures `/solutions` highlights actionable solutions when available, and surfaces an honest `Historical Run Notice` when all runs predate a cohort reset.
2. *Why did we display compact policy badges + a 3-card Decision Guide on `/solutions` while keeping `/recommendations/<run_id>` as a dedicated page?*
   - Progressive disclosure reduces cognitive load: coordinators immediately see *which* alternative wins Student Preference, Skill Fit, or Egalitarian Fairness right on the solution cards, and click through to `/recommendations/<run_id>` when they want to audit the full Calculated Evidence vs. Policy Advice separation required by Section 9 of the TECH5 specification.
3. *How is Student Viewer privacy preserved on `/solutions`?*
   - Aggregate metrics (`mean_skill_fit`, `mean_rank`, `rank_gini`) and policy focus titles contain zero personal identifiers, while `selected_run.diagnostics` (`warnings`, `reasons`, `errors`, `notes`)—which can name individual students—are gated behind `can_view_records`.

## 6. Iterative Update — Unified View Across Dashboard (`View Solutions →`) & Navbar (`Solutions`)
- **User Feedback:** Clicking `View Solutions →` from Dashboard (`/runs/<run_id>`) and clicking `Solutions` from the navbar (`/solutions`) should display the **same unified page**: keeping the clean body layout from the original run-detail view (`Run Diagnostics & Solver Notes` -> `Decision-Support Recommendations Available` banner + `Recommended:` badge bar -> clean `Generated Feasible Solutions` cards), paired with the top `Solutions & Decision Overview` header + `Run:` dropdown (with the clicked run selected) and the bottom `Delete Solutions` card.
- **Architectural Refinement (DRY Controller Helper `_render_solutions_page`):**
  - Extracted `_render_solutions_page(selected_run, recent_runs, usable_ids)` in `app/visualization/routes.py` so both `solutions_overview()` (`GET /solutions`) and `view_run()` (`GET /runs/<run_id>`) render `solutions.html` with zero template duplication.
  - Always renders `#runSelect` whenever runs exist (appending `selected_run` if older than the 25-run window) so whichever run is clicked on Dashboard is visibly `selected` in the dropdown.
  - Updated `solutions.html` body to use the streamlined `run_detail` layout (diagnostics panel above `Decision-Support Recommendations Available` + single-line `Recommended:` badge strip + clean Alternative cards) followed by the `Delete Solutions` (`POST /clear-solutions`) card for `ADMIN` and `COORDINATOR`.
  - Expanded `test_solutions_page_empty_populated_switcher_and_stale_states` in `tests/test_visualization_component.py` to assert parity between `GET /solutions?run_id=<id>` and `GET /runs/<id>`, including `selected` state on `#runSelect` and presence of the `Delete Solutions` form.
