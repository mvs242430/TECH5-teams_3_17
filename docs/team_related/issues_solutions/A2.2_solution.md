## 1. Architectural Pattern & Design Rationale
- **Pattern Applied:** Transparent Decision-Support Presentation Layer (Evidence vs. Normative Advice separation in Jinja2 templates).
- **Why Chosen:** Section 9 of the TECH5 specification requires recommendations to be inspectable and to strictly separate objective mathematical **Evidence** (calculated indicators) from normative **Policy Advice** (value judgements), while exposing the explicit evaluation criteria (`criteria_used`). All recommendation generation logic already resides in `app/engine/recommendations.py` (`generate_recommendations`), so Component A presents those structured `RecommendationItem` objects cleanly without duplicating engine logic.
- **Component Scope:** `app/visualization/templates/recommendations.html`, `app/visualization/templates/run_detail.html`.

---

## 2. High-Level Logic & Data Flow Walkthrough
1. **Run Detail Summary (`run_detail.html`):** When a run has feasible solutions and recommendations, `run_detail.html` renders both the call-to-action banner and a compact at-a-glance badge strip showing which alternative won each priority focus (`Student Preference Maximization`, `Project Skill Quality & Delivery Assurance`, `Balanced & Egalitarian Allocation`), linking directly to `#rec-1`, `#rec-2`, and `#rec-3` on `/recommendations/<run_id>`.
2. **At-a-Glance KPI Strip (`recommendations.html`):** Displays 3 top-level summary cards with color-coded left borders (`kpi-accent-1`, `kpi-accent-2`, `kpi-accent-3`) and direct links to inspect each recommended solution.
3. **Visual Separation of Evidence vs. Advice (`recommendations.html`):**
   - **Left Column:** Renders **Calculated Evidence (Objective Facts)** inside a blue `.alert.alert-info` box (`rec.evidence`), followed by a **"Why this one?"** box listing every criterion in `rec.criteria_used`.
   - **Right Column:** Renders **Policy Advice & Justification** inside a visually distinct green `.alert.alert-success` box (`rec.advice`), accompanied by a governance note.
4. **Direct Cross-Comparison Link:** When 2 or more recommendations exist, each card header includes a **"Compare vs Alt #..."** button linking directly to `/compare?sol1=<this_sol_id>&sol2=<next_sol_id>`.
5. **Empty-Solution Fallback:** When `recommendations` is empty (such as on an `INFEASIBLE` or `INVALID_INPUT` run), the page displays a clear explanation card rather than rendering a blank screen.

## 5. Check Your Understanding (Pedagogical Checkpoint)
1. *Why is it critical in a Decision Support System (DSS) to visually separate "Calculated Evidence" from "Policy Advice"?*
   - **Defense:** A DSS supports human decision-makers rather than replacing them. Objective metrics (mean preference rank, mean skill fit, Gini coefficient) are verifiable mathematical facts (`rec.evidence`), whereas choosing to prioritize student morale over client skill delivery is a policy judgement (`rec.advice`). Separating them prevents algorithmic opacity.
2. *How does the "Compare vs Alt #..." button on `recommendations.html` connect `A2.2` to `A2.1`?*
   - **Defense:** Using Jinja's modular index `{% set next_rec = recommendations[(loop.index) % recommendations|length] %}`, each recommendation card builds a URL `url_for('visualization_web.compare_solutions', sol1=rec.recommended_solution_id, sol2=next_rec.recommended_solution_id)` so coordinators can immediately inspect the student-by-student trade-offs between two recommended alternatives.
