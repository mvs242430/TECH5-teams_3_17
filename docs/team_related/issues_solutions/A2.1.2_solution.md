## 1. Architectural Pattern & Design Rationale
- **Pattern Applied:** MVC Controller & View State Enrichment (`app/visualization/routes.py` + Jinja2 templates), combined with the Repository Pattern (`RunRepository.list_solution_ids_with_assignments()`) and the Internal Component Contract (`AssignmentEngineContract.compare_solutions`).
- **Why Chosen:** Selecting default comparison candidates, resolving single-parameter navigation links (`?sol1=<id>`), and communicating UI empty states are purely presentation-layer responsibilities that belong in Component A (`app/visualization/`). Component B (`app/engine/`) remains strictly headless Python, and database access stays encapsulated inside `RunRepository`. Reusing `list_solution_ids_with_assignments()` across `dashboard()`, `view_run()`, and `compare_solutions()` eliminates the contradiction where Dashboard advertised past runs as active `3 solution(s)` after a scenario reload while `/compare` rendered blank dropdowns.
- **Component Scope:** `app/visualization/routes.py`, `app/visualization/templates/compare.html`, `app/visualization/templates/dashboard.html`, `app/visualization/templates/run_detail.html`, `app/visualization/templates/solutions.html`, `tests/test_visualization_component.py`. Zero edits to `app/engine/`, `app/contract/`, or `app/persistence/`.

## 2. High-Level Logic & Data Flow Walkthrough
1. **Why past runs lose allocations on scenario load:** Clicking **Load Scenario** calls `RunRepository.clear_all_cohort_data()`, deleting `students` and `projects`. Because `assignments` carries `ON DELETE CASCADE` on `student_id` and `project_id`, historical student allocations are removed while `assignment_runs` and `solutions` rows remain.
2. **Consistent stale-run state across views:**
   - `dashboard()` computes `emptied_run_ids` using `list_solution_ids_with_assignments()` so emptied historical runs display `Allocations cleared (cohort reloaded)` beneath `3 solution(s)`.
   - `view_run()` delegates to `_render_solutions_page()` (`solutions.html`), which gates `is_stale_run` via `list_solution_ids_with_assignments()` to warn when an old run's allocations were cleared when cohort data was reloaded, and shows a direct **Compare Alt #1 vs Alt #2 →** button when `>= 2` usable solutions exist (`run_detail.html` carries matching markup).
   - `_enrich_comparison_names()` preserves `A2.4.1` role privacy by populating `student_map` only when `auth.can_view_student_records()` is `True`, so `STUDENT` sees pseudonymized `student_id` codes without display names on `/compare`.
   - `compare_solutions()` passes `has_emptied_runs = bool(recent_runs) and not all_solutions` so `compare.html` replaces empty `<select>` boxes with a clear explanation and a **Go to Dashboard →** button.
3. **Navbar default preselection & auto-compare (`GET /compare`):**
   - When neither `sol1` nor `sol2` is supplied and `all_solutions` is non-empty, `_auto_select_and_compare()` selects `Alt #1` and `Alt #2` from the newest run that has at least two usable solutions (falling back across runs if each run holds one solution).
   - Unless the request arrived from a failed comparison redirect (`danger` flash present in `flask.session`), `_execute_engine_comparison()` immediately computes and enriches the `RunComparison` DTO so the full comparison renders on first load without extra clicks. After an error redirect, the dropdowns still preselect valid defaults while keeping `comparison=None` so another pair's numbers never appear beneath an error banner.
4. **Single-parameter preselection (`GET /compare?sol1=<id>` or `?sol2=<id>`):**
   - Restores the single-ID behavior from the reference implementation while honoring `A2.1.1` safety checks: validates that the requested solution exists and still has assignments (flashing `danger` and redirecting to `/compare` otherwise), then pairs it via `_compare_with_companion()` with a cohort-compatible sibling solution (preferring the same run first) and renders their comparison.
5. **Two-parameter comparison (`GET /compare?sol1=<id>&sol2=<id>`):**
   - Preserves the exact validation, `ValueError` cohort-mismatch guard, and `RunComparison` enrichment flow from Issues `A2.1` and `A2.1.1`.

## 5. Check Your Understanding (Pedagogical Checkpoint)
1. *Why did all 8 historical `COMPLETED` runs disappear from `/compare` after loading a benchmark scenario even though `dashboard.html` still showed `3 solution(s)`?*
   - **Defense:** `load_scenario` calls `clear_all_cohort_data()`, deleting rows from `students` and `projects`. `schema.sql` defines `ON DELETE CASCADE` on `assignments(student_id)` and `assignments(project_id)`, wiping all student allocations while leaving `assignment_runs` and `solutions` metadata intact. `dashboard` reads metadata only, whereas `compare_solutions` filters by `list_solution_ids_with_assignments()`.
2. *Why does `compare_solutions()` suppress auto-computing `comparison` when a `danger` flash is queued in `flask.session`?*
   - **Defense:** When a user requests an invalid or cross-cohort comparison, the route flashes a red error and redirects to `/compare`. Rendering KPI deltas for two *different* default solutions right beneath that red error banner would mislead the user into reading the wrong numbers; preselecting valid dropdown options with `comparison=None` keeps the error honest.
3. *How does `_auto_select_and_compare()` respect the modular monolith boundary?*
   - **Defense:** Component A selects candidate solution IDs via `RunRepository` and delegates all delta math and student-cohort validation strictly through `AssignmentEngineContract.compare_solutions()`, enriching display names only after the DTO is returned.
