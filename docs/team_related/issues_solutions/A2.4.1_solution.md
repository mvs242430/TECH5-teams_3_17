**Issue Title:** Issue A2.4.1 — Role UI & Scenarios Access Cleanup (Coordinator & Student Viewer)

**Date:** 2026-11-03  
**Author / Lead:** Team A (Visualization & RBAC)  

---

## 1. Architectural Pattern & Design Rationale
- **Pattern Applied:** **Policy-Based RBAC Guard + Conditional View Rendering (Blueprint / MVC)**
- **Why Chosen:**
  - Under `docs/architecture.md` §6, only the Course Administrator (`ADMIN`) may edit baseline cohort definitions (`students`, `projects`, `skills`, and benchmark scenario seeding).
  - Previously, `COORDINATOR` and `STUDENT` saw unusable UI containers (an empty `+ Add New Skill` card on `/skills`, a `Quick Benchmark Scenarios` warning card on `/`, and a `Scenarios` navigation tab / `/scenarios` page whose actions they could never execute) plus an overly verbose navbar label (`Programme Coordinator (Runs & Analysis)`).
  - Enforcing `auth.can_edit_cohort_data()` consistently at **both** the Flask route boundary (`GET /scenarios`) and the Jinja2 template layer (`can_edit` context flag) eliminates dead UI panels while guaranteeing server-side refusal if a non-Admin navigates to `/scenarios` directly.
- **Component Scope:** Strictly confined to **Component A (`app/visualization/`)**, documentation (`docs/architecture.md`), and visualization tests (`tests/test_visualization_component.py`). Zero changes to `app/engine/`, `app/contract/`, or `app/persistence/`.

## 2. High-Level Logic & Data Flow Walkthrough
1. **Role Label Resolution (`auth.py` -> `routes.py` -> `base.html`):**
   - `UserRole.ALL_ROLES[UserRole.COORDINATOR]` is set to `"Coordinator"`.
   - `inject_template_globals()` passes `all_roles` and `current_role` to every template, so `base.html` renders `Role: Coordinator` in the navbar (and `"Coordinator"` in the Admin role selector), while keeping `Administrator (Full Control)` and `Student Viewer (Read Only)` prefixes intact.
2. **Skill Catalog View (`GET /skills` -> `skills.html`):**
   - When `can_edit` is `True` (`ADMIN`), `skills.html` renders `class="grid-2"` with the **Competence & Skill Catalog** table on the left and the **+ Add New Skill** form card on the right.
   - When `can_edit` is `False` (`COORDINATOR` and `STUDENT`), `class="grid-2"` and the entire **+ Add New Skill** card (plus the empty-state form hint) are omitted, allowing the catalog table to span the full container width cleanly (matching `/students` and `/projects`).
3. **Scenarios Route & Navigation (`GET /scenarios`, `base.html`, `dashboard.html`):**
   - **Route Guard:** `scenarios_page()` (`GET /scenarios`) checks `auth.can_edit_cohort_data()` first. If `False`, it flashes `"Permission denied for current role."` (`danger`) and redirects to `visualization_web.dashboard` (`/`).
   - **Navbar & Dashboard Parity:** `base.html` wraps the `Scenarios` navigation link in `{% if can_edit %}`, and `dashboard.html` wraps both `class="grid-2"` and the **Quick Benchmark Scenarios** card in `{% if can_edit %}` so `COORDINATOR` and `STUDENT` see no unreachable links to `/scenarios` and no dead warning card alongside the optimization trigger panel.

## 5. Check Your Understanding (Pedagogical Checkpoint)
Key self-check questions for student grading defense:
1. *Why do we guard `GET /scenarios` in `routes.py` instead of only hiding the `Scenarios` link in `base.html` and `dashboard.html`?*
   - Hiding a link in HTML is a UX improvement, not an access control check: a `COORDINATOR` or `STUDENT` could still type `/scenarios` in the browser address bar. Checking `auth.can_edit_cohort_data()` inside `scenarios_page()` enforces authorization on the server before rendering the template.
2. *Why did we also make `class="grid-2"` conditional (`<div{% if can_edit %} class="grid-2"{% endif %}>`) in `skills.html` and `dashboard.html`?*
   - In `style.css`, `.grid-2` uses `grid-template-columns: 1fr 1fr`. When the right-hand card (`+ Add New Skill` or `Quick Benchmark Scenarios`) is omitted for non-Admin roles, keeping `.grid-2` would squeeze the remaining card into the left 50% column and leave blank whitespace on the right.
3. *How does this implementation preserve Component A / Component B architectural boundaries?*
   - Role state (`flask.session`) and UI visibility live exclusively in Component A (`app/visualization/`). Component B (`app/engine/`) and `AssignmentEngineContract` (`app/contract/`) remain completely untouched and framework-independent.

## 6. Iterative Update — Compact `Student` Navbar Label
- **User Feedback:** The navbar badge for `STUDENT` also showed `Role: Student Viewer (Read Only)` and should display `Role: Student` (matching `Role: Coordinator`).
- **Architectural Refinement (`NAV_LABELS` vs `ALL_ROLES` Separation):**
  - Baseline starter test `test_role_switcher` (`tests/test_visualization_component.py`) asserts `b"Switched role to Student Viewer"` in the flash banner emitted by `POST /set-role`.
  - Rather than mutating `UserRole.ALL_ROLES` (which powers descriptive flash messages), we introduced `UserRole.NAV_LABELS = {ADMIN: "Administrator", COORDINATOR: "Coordinator", STUDENT: "Student"}` in `app/visualization/auth.py`, injected `nav_role_labels` in `inject_template_globals()` (`app/visualization/routes.py`), and bound `base.html` to `nav_role_labels`.
  - Expanded `test_navbar_displays_short_role_labels` in `tests/test_visualization_component.py` to verify both `Role: <strong>Coordinator</strong>` and `Role: <strong>Student</strong>` while keeping all starter tests untouched and passing (`251 passed`).

## 7. Iterative Update — Pseudonymized Student Allocations (`student_id` Only, No Name)
- **User Feedback:** On **Student-to-Project Allocations** (`/solutions/<id>`) and **Detailed Allocation Shifts** (`/compare`), the `STUDENT` role should see each row's `student_id` (`S01`, `S02`, ...) and **no** `display_name`.
- **Server-Side Pseudonymization & Template Changes:**
  - `app/visualization/routes.py`: In both `view_solution()` and `compare_solutions()`, `StudentRepository().list_all()` is queried only when `auth.can_view_student_records()` is `True` (defaulting to `{}` for `STUDENT`), so `display_name` values never enter template memory for `STUDENT`.
  - `app/visualization/templates/solution_detail.html` & `app/visualization/templates/compare.html`: Render the allocation and shift tables for all roles, displaying `<th>Student ID</th>` and `<code>{{ student_id }}</code>` when `can_view_records` is `False`, and `<th>Student</th>` with `<strong>{{ display_name }}</strong>` + `ID: <code>{{ student_id }}</code>` for `ADMIN` and `COORDINATOR`.
  - `docs/architecture.md` (§6.1) & `tests/test_visualization_component.py`: Updated §6.1 notes/table and added `test_allocation_tables_show_ids_without_names_for_student` (`6` parametrized cases across `ADMIN`, `COORDINATOR`, `STUDENT` × `solution`, `compare`) while verifying zero `display_name` leaks on every `STUDENT` page.
