## 1. Architectural Pattern & Design Rationale

- **Pattern Applied:** Role-based access control with a *guard clause* at the start of each Flask route (the controller in our MVC / Blueprint split). Each guard calls one *policy helper* in `app/visualization/auth.py`. The context processor `inject_template_globals` passes the same helpers to the templates, so a button and its route cannot disagree.
- **Why Chosen:** Every request passes through its route, so a check there cannot be skipped by posting to the URL directly. Hiding a button only makes the page easier to use. The real protection is the server-side check.
- **Component Scope:**
  - `app/visualization/auth.py`: one new helper, `can_manage_fixed_assignments()`.
  - `app/visualization/routes.py`: the two fixed-assignment routes and `lock_and_rerun` use the new helper. One new template flag. Two refusal messages are unified.
  - `app/visualization/templates/fixed_assignments.html` and `solution_detail.html`: the buttons follow the new flag.
  - `tests/test_visualization_component.py`: new tests only.
  - `docs/architecture.md`: new §6.1 "Role × Action Table".
  - `app/contract/`, `app/domain/`, `app/persistence/` and `app/engine/` are not changed.

### Design choice: a new helper instead of reusing `can_trigger_optimization()`

`can_trigger_optimization()` already allows Admin and Coordinator, so the lock routes could simply call it. We added `can_manage_fixed_assignments()` instead. It allows the same two roles today, but it asks a different question:

| Helper | Question it answers | Roles |
| :--- | :--- | :--- |
| `can_edit_cohort_data()` | May this role change the cohort (students, projects, skills, scenarios)? | Admin |
| `can_trigger_optimization()` | May this role run the solver, or delete runs? | Admin, Coordinator |
| `can_manage_fixed_assignments()` *(new)* | May this role change the solver's fixed-lock inputs? | Admin, Coordinator |

With one shared helper, a future rule such as "only the Admin may run the solver" would also silently take lock rights away from the Coordinator. A separate helper keeps the two rules apart. The route also reads clearly: `if not auth.can_manage_fixed_assignments()`.

`lock_and_rerun` does both things: it saves a fixed lock, then runs the solver. It now checks **both** helpers. Today this changes nothing for any role, but if one rule changes later the route stays correct.

The template flag is named `can_manage_locks`, next to the existing `can_edit` and `can_optimize`.

## 2. High-Level Logic & Data Flow Walkthrough

1. **Request:** for example, a Coordinator submits the lock form, which sends `POST /fixed-assignments/new`.
2. **Role lookup:** the route calls `auth.can_manage_fixed_assignments()`, which reads the role from the Flask session (`get_current_role()`) and returns `True` for `ADMIN` or `COORDINATOR`.
3. **Refused (Student Viewer):** the route flashes "Permission denied for current role." as `danger` and redirects to `/fixed-assignments`. No repository method is called, so nothing is saved.
4. **Allowed:** the route reads the form, calls `FixedAssignmentRepository().save(...)` and flashes "Fixed assignment created …". Releasing a lock works the same way with `FixedAssignmentRepository().delete(student_id)`.
5. **Templates:** `inject_template_globals` adds `can_manage_locks`. `fixed_assignments.html` shows the "Action" column, the **Release** buttons and the lock form only when it is true. Otherwise it shows a notice naming the current role. `solution_detail.html` shows the **Lock & Rerun** column only when `can_optimize and can_manage_locks` is true, which matches the route's two checks.

## 5. Check Your Understanding (Pedagogical Checkpoint)

1. *Why is the check in the route and not only in the template?* Hiding the button does not stop someone from posting to the URL directly. The route is the one place every request passes through.
2. *Why add `can_manage_fixed_assignments()` when `can_trigger_optimization()` already allows the same roles?* They are different rules: running the solver vs. changing its inputs. With one shared helper, changing one rule would silently change the other.
3. *Why does `lock_and_rerun` check two helpers?* It does two things: it saves a lock, then runs the solver. The role needs both rights.
4. *How does `test_student_viewer_cannot_mutate` know that "nothing changed"?* `_db_snapshot()` reads every row of every table before and after the request and compares the two snapshots. Any insert, update or delete anywhere shows up.
5. *Why is there an Admin control test?* If the form data were invalid, the route might refuse the request for that reason, and the Student Viewer test would pass even with no role check. The control test shows that each request really changes data when it is allowed.
6. *What happens when a teammate adds a new `POST` route?* `test_mutating_route_list_covers_every_post_route` fails until the route is added to `MUTATING_ROUTES`, which then also tests it as a Student Viewer.
7. *Which boundaries are respected?* All changes are in Component A (`app/visualization/`), the tests and the docs. The engine, contract, domain and persistence layers are not touched.
