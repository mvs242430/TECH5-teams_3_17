## Architectural Pattern & Rationale (Explain-Before-Accept)

Before committing these changes, here is the complete architectural rationale for how **Issue A1.1** was solved:

### 1. Architectural Patterns Applied
- **Model-View-Controller (MVC) / Flask Blueprint Pattern (`app/visualization/routes.py`):**
  - Routes act as the **Controller**: they unpack HTTP POST form data, enforce authentication/authorization rules, trigger business validation, orchestrate repository mutations, and redirect back to the View with flashed session messages.
  - `skills.html` acts as the **View**: it renders catalog data and conditionally exposes admin-only forms and action buttons based on template context (`can_edit`).
- **Repository Pattern (`app/persistence/repositories.py`):**
  - All database interactions are encapsulated behind [SkillRepository](file:///Users/mavenclu/Documents/NHH/_ted-semester/tech5/_project/TECH5-teams_3_17/app/persistence/repositories.py#L15-L71), [StudentRepository](file:///Users/mavenclu/Documents/NHH/_ted-semester/tech5/_project/TECH5-teams_3_17/app/persistence/repositories.py#L73-L225), and [ProjectRepository](file:///Users/mavenclu/Documents/NHH/_ted-semester/tech5/_project/TECH5-teams_3_17/app/persistence/repositories.py#L227-L300). The route controller does not write raw SQL queries, keeping concerns separated.
- **Role-Based Access Control (RBAC) (`app/visualization/auth.py`):**
  - Authorization is verified server-side at the start of mutating routes via `auth.can_edit_cohort_data()`. Even if an unauthorized client makes a direct HTTP POST request, access is blocked with a `"Permission denied"` flash message.

## Architectural Pattern & Rationale (Explain-Before-Accept)

### 1. Architectural Pattern Applied: Sticky Form State in MVC
- **Pattern:** *Sticky Form / State Preservation Pattern* in Model-View-Controller architecture.
- **Why this pattern:** 
  Previously, when a validation error occurred (e.g., entering an existing skill ID or invalid format), `create_skill` issued an HTTP 302 redirect back to `/skills`. In standard HTTP, a redirect initiates a fresh GET request, discarding all unsaved `POST` form data and frustrating users who have to retype long names and descriptions.
  
  By contrast, with the **Sticky Form pattern**:
  - Upon a validation error, the controller captures the submitted fields in a `form_data` dictionary:
    ```python
    form_data = {
        "id": skill_id,
        "name": name,
        "description": description,
    }
    ```
  - It re-renders `skills.html` directly (HTTP 200) passing both the catalog `skills` and `form_data`.
  - In `skills.html`, input fields bind their values to `form_data`:
    ```html
    value="{{ form_data.id if form_data else '' }}"
    value="{{ form_data.name if form_data else '' }}"
    <textarea ...>{{ form_data.description if form_data else '' }}</textarea>
    ```
  - When the user types an existing identifier, the red warning message appears, but **all their entered data remains in the form inputs**, allowing them to simply adjust the identifier and resubmit.
