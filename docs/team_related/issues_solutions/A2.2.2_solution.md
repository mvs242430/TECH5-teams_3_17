## 2. High-Level Logic & Data Flow Walkthrough
1. **Engine-to-View Data Flow:**
   - `GET /recommendations/<run_id>` (`view_recommendations` in `app/visualization/routes.py`) loads the persisted `AssignmentRun` via `RunRepository.get_run(run_id)`, computes the three `RecommendationItem` objects via `recommendations.generate_recommendations(run.solutions)`, and passes `recommendations` into `recommendations.html`.
2. **Root Cause of Broken Grid Layout (HTML5 Nested Anchor Adoption Agency):**
   - Previously, the top `.kpi-grid` summary strip wrapped each `.kpi-card` in `<a href="#rec-{{ loop.index }}" class="kpi-card ...">` while nesting a second `<a href="/solutions/...">View solution &rarr;</a>` inside `<span class="kpi-sub">`.
   - Under the HTML5 specification, `<a>` elements cannot contain interactive descendants (such as another `<a>`). When parsing the inner `<a href="/solutions/...">`, the browser automatically closed the outer `<a class="kpi-card">` (closing the still-open `<span class="kpi-sub">` inside it as well) and inserted the inner `<a ...>View solution →</a>` directly into `.kpi-grid` as a sibling grid item—producing 6 grid children instead of 3 and floating standalone `View solution →` links beside and beneath the cards. The leftover `</span>` and outer `</a>` closing tags then match no open element and are ignored.
3. **Clean Cards-Only Summary Strip:**
   - Removing `<span class="kpi-sub"><a ...>View solution &rarr;</a></span>` leaves strictly the three valid `<a href="#rec-{{ loop.index }}" class="kpi-card ...">` summary cards inside `.kpi-grid`, each displaying `{{ rec.priority_focus }}` and `Alt #{{ rec.recommended_alternative_number }}`.
   - Clicking any top card smoothly scrolls to its corresponding `#rec-1`, `#rec-2`, or `#rec-3` section below, where the card header already provides **View Solution #N →** and **▶ Compare vs Alt #M** buttons.

## 5. Check Your Understanding (Pedagogical Checkpoint)
1. *Why did `View solution →` appear outside and underneath the summary cards in the browser even though in the template source it was written inside `<a class="kpi-card">...</a>`?*
   - **Defense:** HTML5 forbids nesting an `<a>` element inside another `<a>` element. When the browser's HTML5 parser encountered the inner `<a href="/solutions/...">`, it implicitly closed the outer `<a href="#rec-..." class="kpi-card">` first, turning each `View solution →` link into a separate sibling cell inside the CSS `.kpi-grid`.
2. *Does removing `View solution →` from the top cards remove the user's ability to open a recommended solution?*
   - **Defense:** No. Clicking a top card jumps directly to `#rec-1`, `#rec-2`, or `#rec-3` on the same page, and each recommendation detail card's `.card-header` retains its primary **View Solution #N →** button alongside **Compare vs Alt #M**.
3. *Why were no files in `app/engine/` or `app/persistence/` touched?*
   - **Defense:** Recommendation selection (`generate_recommendations`) and run retrieval (`RunRepository`) are unchanged; only the Jinja2 HTML presentation in Component A (`app/visualization/templates/recommendations.html`) changed, preserving modular monolith decoupling.
