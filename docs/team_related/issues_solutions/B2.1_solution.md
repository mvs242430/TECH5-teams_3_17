## 1. Architectural Pattern & Design Rationale
- **Pattern Applied:** Builder Helper Pattern (`_build_base_model`) inside Component B (`app/engine/strategies.py`) using **Pyomo** (`pyomo.environ.ConcreteModel`) and the **HiGHS** MILP solver (`appsi_highs`).
- **Why Chosen:** All optimization strategies share the same feasible region defined by hard assignment constraints. Centralizing decision variable creation and hard constraint registration in `_build_base_model` avoids code duplication across strategies and guarantees that hard constraints are never violated regardless of the objective function.
- **Component Scope:** `app/engine/strategies.py`, `requirements.txt` (Issue `0.3`), `tests/test_solvers.py`.

---

## 2. High-Level Logic & Data Flow Walkthrough
1. **Binary Decision Variables:** Creates binary variables $x_{s,p} \in \{0, 1\}$ (`domain=pyo.Binary`) for every $(s, p) \in S \times P$.
2. **Single-Allocation Constraint:** For each student $s \in S$, enforces $\sum_{p \in P} x_{s,p} = 1$.
3. **Project Capacity Bounds:** For each project $p \in P$, enforces $l_p \le \sum_{s \in S} x_{s,p} \le u_p$ (`min_capacity` to `max_capacity`).
4. **Mandatory Skill Eligibility:** For each pair $(s, p)$, if project $p$ has any mandatory requirement $r$ (`is_mandatory=True`) where student $s$'s proficiency is strictly below `minimum_level`, adds $x_{s,p} = 0$.
5. **Fixed Assignment Locks:** For each pre-allocated lock $(s^*, p^*) \in F$ whose student and project exist in the cohort, adds $x_{s^*, p^*} = 1$.
6. **Solver Configuration:** Attaches `pyo.SolverFactory("appsi_highs")` configured with `Config.PULP_TIME_LIMIT_SECONDS`.

## 5. Check Your Understanding (Pedagogical Checkpoint)
1. *Why are mandatory skills modeled as $x_{s,p} = 0$ hard constraints while nice-to-have skills are modeled in the objective function?*
   - **Defense:** A mandatory requirement is a hard eligibility rule that must never be violated in any feasible solution, whereas a nice-to-have skill is a soft preference traded off against student rank satisfaction via `calculate_assignment_skill_fit`.
2. *How does `_build_base_model` guarantee that fixed assignments from Scenario 2 are preserved across all strategies?*
   - **Defense:** Because $x_{s^*, p^*} = 1$ and $\sum_{p \in P} x_{s^*, p} = 1$ are structural constraints in the base model, every strategy built on top of `_build_base_model` is forced to assign $s^*$ to $p^*$.
