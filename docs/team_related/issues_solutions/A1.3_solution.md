## Issue A1.3 — Friendly Messages for Bad Data

### 1. Architectural Pattern & Rationale
- **Controller-side validation (MVC):** the route functions in `app/visualization/routes.py` check the form *before* anything reaches the repositories. A bad value gives a red flash message and the data is not saved; the user never sees an error page.
- **Defence in depth:** the HTML inputs have `min`/`max`, but a browser check can be skipped (e.g. a direct POST, which is exactly what the tests do). The server check is the one that counts, and the SQLite `CHECK` / key constraints in `schema.sql` are the last line of defence.
- **One rule, one place (DRY):** student validation lives in helper functions shared by `create_student` and `update_student`, so creating and editing a student always follow the same rules. Project validation stays in `_parse_and_validate_project_form`, already shared by create and edit (A1.2).

### 2. The 8 Cases
| Case | Before A1.3 | After A1.3 |
|---|---|---|
| min seats > max seats | already handled | test added |
| negative / empty capacity | negative and non-numbers handled | clear message for empty fields; max must be ≥ 1 (same as the schema `CHECK`) |
| skill id that does not exist | silently ignored | red message (project and student forms) |
| skill level outside 1–5 | project: silently dropped; student: **level 9 was saved** | red message, nothing saved |
| duplicate project / student id | already handled | tests added; empty student id is now checked before the duplicate check |
| preference for unknown project | already handled | test added |
| same rank used twice (project listed twice) | silently removed | red message — a project can have only one rank |
| fewer than 3 preferences | no message | **warning only**, the student is still saved |

### 3. Logic & Data Flow (student form)
`create_student` / `update_student` → `_validate_student_skills_and_preferences(student_id)`:
1. `_parse_student_skills` reads every `skill_<id>` field: empty or 0 = no skill, otherwise a whole number 1–5 for a skill that exists, else an error.
2. `_parse_and_validate_preferences` (existing) turns `"P1, P2, P3"` into ranked `Preference` objects and lists unknown ids.
3. `_find_repeated_preferences` finds projects listed twice (case-insensitive, like step 2).
4. Returns `(skills, preferences, errors, warnings)`: any error → red messages and redirect back to the form; warnings → yellow message, then save.
