## Issue A1.4 — Database & SQL Documentation (Deliverable 5)

### 1. Architectural Pattern & Rationale
- **Single source of truth for SQL:** the analytical queries live only in `app/persistence/queries.sql`. Section 5 of `docs/database_design.md` copies the SQL from that file, so the document and the code cannot drift apart again (before this issue they did: the document showed different queries than the file).
- **Repository Pattern boundary:** the queries read the same 3NF tables that the repositories (`app/persistence/repositories.py`) write. Nothing in the application code was changed; this issue documents and verifies the persistence layer.
- **Evidence over claims:** every query was executed on real scenario data and its real output is pasted into the document, as Deliverable 5 asks.

### 2. Logic & Data Flow
1. **Schema check.** `docs/database_design.md` was compared table by table with `app/persistence/schema.sql`. Result in section 7 of the document: tables, keys, `CHECK` rules and cascades match; the indexes were missing (added as section 3.11); composite unique keys were shown as single-column `UK` in the ER diagram (clarified); section 5 did not match `queries.sql` (rewritten).
2. **Running the queries.** A throw-away script (kept outside the repository, as the issue asks) did exactly what a user does in the browser:
   - start the app with an empty database,
   - load a scenario (`/load-scenario/standard`, `fixed`, `infeasible`),
   - trigger a run (`/runs/trigger`, strategy `PREFERENCE`, 2 alternatives),
   - execute each query in `queries.sql` against that SQLite file with `:solution_id` = alternative 1,
   - print each result as a Markdown table.
3. **Two new queries** added to `queries.sql`:
   - **Query 7 — students assigned to a project they did not rank.** Anti-join (`LEFT JOIN preferences ... WHERE pr.project_id IS NULL`). It checks the `preferences` table directly instead of trusting `assignments.preference_rank`.
   - **Query 8 — project demand vs. supply before optimisation.** Conditional aggregation (`SUM(CASE WHEN rank = 1 ...)`) of first choices per seat. Uses input data only, so it works before any run.

### 3. Findings (section 6 of the document)
- Query 7 found that `MockAssignmentEngine` stores `preference_rank = 1` for projects a student never ranked (`get_preference_rank(...) or 1` in `app/contract/mocks.py`), so query 3 over-reports first choices. The real engine must store `NULL` for unranked projects.
- The mock writes placeholder `skill_fit_score = 0.85` and `unmet_requirements = []`, while query 4 finds 8 real skill gaps.
- Query 8 explains the infeasible scenario before solving: 6 seats for 10 students.
- All solution-dependent numbers come from the mock engine and must be re-run after issue X1 (real engine swap).
